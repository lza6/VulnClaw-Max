## 0. 一页摘要

### 0.1 结论

VulnClaw 的**内核**（模型主导的 solve 循环、证据记忆、子 Agent 扇出、上下文预算、断点快照、约束策略、执行门禁）已经达到可交付水准；短板集中在**运行外壳**：Web 后端的任务生命周期、事件流、持久化、并发治理，以及产品层的「项目 / 发现 / 报告 / 集成」交付链路。

三个判断：

1. **功能不是瓶颈，状态一致性与失败语义才是。** 当前一次 LLM 鉴权失败会被记成「任务完成、`exit_code=0`」，CLI 静默退出且返回 0。这会让自动化流水线和操作者对工具产生错误的信任。
2. **Web 后端目前只适合「单次、短时、单人、盯屏」使用。** 事件重复投递、无界队列、每事件全量落盘、重启僵尸任务、无并发上限，四条叠加后，长时间运行必然劣化。
3. **前端体验骨架完整，但缺少工程护栏。** 0 个前端测试、0 条 lint、无 E2E；`web/app.py` 覆盖率 60%，正是问题最密集的区域。

### 0.2 五个最高优先级动作

| 顺序 | 动作 | 收益 | 成本 | 风险 |
|------|------|------|------|------|
| 1 | 修「失败被记为成功」的完成语义（P0-01） | 恢复工具可信度，CI 可用 | 1～1.5 人日 | 低（改返回契约 + 预检） |
| 2 | 重做任务事件流：唯一序号 + 环形缓冲 + 心跳 + 续传（P1-02/03/04） | 消除重复/丢事件/内存增长 | 2 人日 | 中（涉及前端订阅） |
| 3 | 任务持久化改为 append-only + 去抖快照 + 保留策略（P1-05） | 写放大从 O(N²) 降到 O(1) | 1.5 人日 | 低（复用已有 `atomic_write_json`） |
| 4 | 任务生命周期闭环：`interrupted` 状态、停止守卫、并发上限、优雅停机（P1-03/06/07） | 长稳运行、可恢复 | 2 人日 | 中（状态机扩展需前后端同步） |
| 5 | 目标列表容错与索引化（P1-08） | 500 目标从 2.7s 降到 <100ms，单坏文件不再拖垮接口 | 0.5～1 人日 | 低 |

### 0.3 本指南刻意不做的事

不换数据库、不引入 Redis/Celery、不把 `WebTaskManager` 改成分布式、不重构 `vulnclaw/cli/main.py`（3,825 行）、不动 Rust TUI 架构、不为本地单用户场景堆鉴权体系、不加任何 feature flag 或兼容层。V2 的目标是**把已有轮子装好**，不是再造一套。

## 2. 缺陷清单

分级口径：P0 = 结果错误/数据不可信；P1 = 主链路在高概率场景下劣化或失效；P2 = 体验/维护性缺陷；P3 = 增强建议。所有条目均给出位置、证据、根因、最小修复与验收方式。

### 2.1 P0

#### P0-01 LLM 调用失败被记为「任务完成、退出码 0」

- **位置**
  - `vulnclaw/agent/core.py:528-531`（`chat()` 的 `except Exception` 把异常转成 `result.output = "[!] Agent 错误: ..."` 后正常返回）
  - `vulnclaw/task_service.py:393-397`（`recon` / `scan` / `exploit` 走 `agent.chat`）
  - `vulnclaw/orchestrator.py:161-168`（只要 `runner` 不抛异常就 `status="completed"; exit_code=0`）
  - `vulnclaw/cli/main.py` 中 `recon`/`scan`/`exploit` 缺少凭据预检（对照 `:1321`、`:1542`、`:1700`、`:3522` 都有 `has_llm_credentials` 检查）
- **证据（可复现）**

```bash
$ python -m vulnclaw recon 127.0.0.1:1
[*] Restored saved target state: 127.0.0.1:1
Thinking... 
$ echo $?
0
```

  Web 侧同一路径：

```
task_created → task_started →
round_output {"text": "[!] Agent 错误: Error code: 401 - Incorrect API key provided: placeholder..."} →
task_completed {"status":"completed"}   # summary.exit_code = 0, status = completed
```

- **根因**：三层叠加。① `chat()` 把可恢复性与失败混为一谈，异常被降级为文本；② 编排层以「是否抛异常」作为唯一完成判据，不检查 `AgentResult` 内容；③ CLI 不打印该 `AgentResult.output`，于是错误连文字都不显示，直接以 0 退出。
- **修复方案（最小改动，不动 REPL 交互语义）**
  1. `core.chat()` 增加关键字参数 `raise_on_error: bool = False`；任务编排路径传 `True`，异常向上抛；REPL 保持默认宽松行为。
  2. 新增 `vulnclaw/agent/errors.py`：`LLMInvocationError`（含 `stage`、`provider`、脱敏后的原始消息），由 `llm_client` 的重试耗尽处抛出。
  3. `run_agent_task()` 捕获该异常 → `status="failed"`、`exit_code=1`、`mark_run_status(...,"failed")`、摘要写 `error`。不要把所有异常都当失败（`KeyboardInterrupt` / `CancelledError` 已有分支，保持不变）。
  4. `recon` / `scan` / `exploit` 三个命令补 `has_llm_credentials` 预检，复用 `_resume_saved_run()` 的写法，提示语沿用 `vulnclaw/i18n` 现有错误文案风格并补齐中英文 key。
  5. CLI 在 `status=="failed"` 时 `err_console.print` 错误摘要并 `raise typer.Exit(1)`；Web 发 `task_failed`。
- **验收**
  - `vulnclaw recon 127.0.0.1:1; echo $?` → 打印可操作错误、退出码 **1**。
  - `POST /api/tasks/run` 在无效 key 下 → 事件为 `task_failed`，`summary.exit_code == 1`。
  - 新增 `tests/agent/test_llm_failure_propagation.py`、`tests/cli/test_cli_failure_exit_code.py`。
- **风险**：交互式 REPL 依赖宽松路径，务必保持默认值；`chat()` 的调用点仅 3 处，改造面可控。

### 2.2 P1

#### P1-02 SSE 事件重复投递（每个订阅者收到两遍）

- **位置**：`vulnclaw/web/task_manager.py:53-59`（`publish` 同时写 `_history` 与 `_queues`）、`:117-134`（`stream_events` 先回放 `history` 再排空 `queue`）；`vulnclaw/web/app.py:192-201`。
- **证据**：单次订阅返回 `task_created, task_started, round_output, task_completed, task_stopped, task_stopped`；第二次订阅因队列已排空而只返回 5 条。
- **根因**：队列与历史是两条独立通道，同一条事件在两条通道各出现一次；没有全局序号，订阅者无法去重。
- **修复方案**：引入单调 `seq`
  1. `TaskEvent` 增加 `seq: int`（`vulnclaw/web/schemas.py`），`publish` 自增并写入 `id: {seq}` SSE 帧（`web/stream.py` 一行改动）。
  2. `stream_events` 记录 `cursor = len(history)`，回放 `history` 后只消费 `seq > cursor` 的队列项；或改为单一环形缓冲 + `asyncio.Condition`（推荐后者，见 5.1）。
  3. 支持 `Last-Event-ID` 请求头：从该 seq 之后回放。
- **验收**：新增 `tests/web/test_task_stream.py`——连续订阅两次，断言序列严格递增、无重复、终态后 0.5 s 内关闭；`Last-Event-ID` 只补缺失区间。
- **风险**：前端 `EventSource` 会自动回传 `Last-Event-ID`，无需额外代码；`seq` 需持久化以支持进程重启后续传。

#### P1-03 `stop` 篡改已完成任务状态，且 `_running` 永不清理

- **位置**：`vulnclaw/web/task_manager.py:135-146`。
- **证据**：任务已 `completed` 后再 `POST /api/tasks/{id}/stop` 返回 200，记录变为 `stopped`（`summary.status` 仍是 `completed`，两处状态自相矛盾）。
- **根因**：`bind_runtime_task` 保存的 `asyncio.Task` 在完成后未移除；`stop_task` 只判断「是否在字典里」，不判断任务当前状态；`set_stopped` 无状态守卫。
- **修复方案**：① `_run_task` 的 `finally` 调用 `manager.unbind_runtime_task(task_id)`；② `stop_task` 仅在 `status ∈ {pending, restoring, running}` 时执行，否则返回 `False`，路由改为 `409 {"detail":"Task already finished"}`；③ `set_stopped/set_completed/set_failed` 增加终态幂等守卫（已是终态则忽略）。
- **验收**：`tests/web/test_task_manager_lifecycle.py`——完成后 stop → `False` 且状态不变；并发两次 stop 只生效一次；终态重复 set 不改变状态。
- **风险**：`404 → 409` 是 API 语义修正，前端需展示「任务已结束」而不是通用错误。

#### P1-04 无消费者的事件队列无界增长

- **位置**：`vulnclaw/web/task_manager.py:40`（`asyncio.Queue()` 无 `maxsize`）、`:53-59`、`:117-134`。
- **证据**：5,000 条事件、无订阅者时 `queue.qsize() == 5001`，耗时 11.17 s，状态文件 210 KB。`persistent` 模式一次运行可产生上万条事件，浏览器刷新或断网后即触发。
- **根因**：队列只被 `stream_events` 消费，客户端断开后消费协程被取消，队列无人排空且从不裁剪。
- **修复方案**：优先用「环形缓冲 + `asyncio.Condition`」替代 per-task 队列（见 5.1）；若保留队列，则 `asyncio.Queue(maxsize=1000)`，满时丢弃最旧并记 `dropped` 计数，客户端重连靠 `Last-Event-ID` 从环形缓冲补。
- **验收**：压测脚本：10,000 事件无消费者 → 内存与队列长度封顶；`tests/web/test_task_stream_backpressure.py`。
- **风险**：丢弃只影响实时流，落盘事件与报告不受影响。

#### P1-05 每个事件全量重写状态文件（O(N²) 写放大）

- **位置**：`vulnclaw/web/task_manager.py:148-159`，调用点 `:44`、`:59`、`:115`。
- **证据**：1 个任务 300 事件 → 1.38 ms/事件（文件 189 KB）；300 个任务后再创建 → 2.179 s（文件 573 KB）。事件数 × 任务数增长时，单次发布成本线性恶化。
- **根因**：`_save_state()` 在每次 `publish` 时序列化**全部任务 + 全部事件历史**并整文件重写，且无保留策略。
- **修复方案**
  1. 事件改为 append-only：`~/.vulnclaw/web/events/<task_id>.jsonl`，复用 `RunContext.append_event` 的写法。
  2. 任务记录（体积小）改为 300 ms 去抖 + `atomic_write_json`（复用 `vulnclaw/run_context.py:375`）。
  3. 启动时按「最近 200 个任务 / 最近 7 天事件」裁剪；裁剪动作写入一次 `task_pruned` 事件便于审计。
- **验收**：基准脚本断言 300 事件 < 50 ms、300 任务创建 < 300 ms、`web_tasks.json` < 100 KB；新增 `tests/web/test_task_persistence.py`。
- **风险**：进程崩溃可能丢最后 300 ms 的任务状态（事件不丢），可接受。

#### P1-06 重启后 `running` 僵尸任务，事件流永不结束

- **位置**：`vulnclaw/web/task_manager.py:161-178`（`_load_state` 原样恢复状态）。
- **证据**：`_load_state` 把 `pending/running/restoring` 原样载入；`stream_events` 的退出条件只认 `completed/failed/stopped`，所以重启前未结束的任务会永远停在 `running`，SSE 每 0.5 s 空转一次，前端一直显示「扫描中」。
- **根因**：缺少进程级生命周期对账；状态枚举没有「被中断」这一语义。
- **修复方案**：启动时把非终态任务映射为新增的 `interrupted`，发 `task_interrupted` 事件并在记录里写 `interrupted_at`；`TaskStatus` 增加该值，前端 `taskLabels` 增加中英文标签与「续跑」入口（复用 `resume=true` 与 `snapshot_id`）。
- **验收**：模拟崩溃（写一份 `running` 状态文件后重启）→ `/api/tasks` 无 `running`，SSE 立即结束；`tests/web/test_task_restart_reconcile.py`。
- **风险**：旧版本状态文件字段兼容；前端映射需同步，否则显示原始枚举值。

#### P1-07 任务无并发上限、无排队、无优雅停机

- **位置**：`vulnclaw/web/services/task_service.py:17-22`（`asyncio.create_task` 直接启动）；`vulnclaw/web/app.py:140-300`（无 shutdown 钩子）。
- **证据**：连续 `POST /api/tasks/run` 会同时创建多个 `AgentCore` 与 `MCPLifecycleManager`，每个都 `start_enabled_servers()`；`uvicorn` 退出时不会 cancel 这些任务，`stop_all()` 只在 `_run_task` 的 `finally` 中执行。
- **根因**：缺少调度层，把「接受请求」等同于「开始执行」。
- **修复方案**：进程内 `asyncio.Semaphore(max_concurrent_tasks)`（配置默认 1，范围 1–4，与子 Agent 的 `max_concurrent` 提示一致）；超出的任务状态为 `queued` 并入 FIFO；`app` 注册 `lifespan` 关闭钩子，逐个 `cancel` + `await` + `stop_all()`；`/api/health` 暴露 `running/queued` 计数。
- **验收**：连续提交 5 个任务 → 仅 1 个 `running`，其余 `queued`；`SIGINT` 后无残留 `nmap`/`npx` 子进程（用 `scripts/verify_execution_boundary.py` 同款断言）；`tests/web/test_task_queue.py`。
- **风险**：用户可能期望并行；默认 1 符合单机工作台定位，配置项写进 `config` 文档。

#### P1-08 目标列表全量解析，单个坏文件拖垮整个接口

- **位置**：`vulnclaw/web/services/target_service.py:26-33`；`_build_target_view` `:82-100`。
- **证据**：500 个目标 → **2.687 s**（仅返回 20 条）；放入一个非法 `state.json` → `JSONDecodeError` 未捕获 → `/api/targets` 返回 500，前端目标下拉整体不可用。
- **根因**：先 `glob` 全量 `json.loads` 再按 mtime 排序取前 N；无单文件隔离。
- **修复方案**：① 先按 `stat().st_mtime` 排序取前 `limit`，再解析；② 每个文件 `try/except (OSError, JSONDecodeError, ValidationError)`，失败时 `logger.warning` 并跳过；③ 第二阶段可维护 `~/.vulnclaw/targets/index.json`（追加写 + 定期重建），接口签名不变。
- **验收**：500 目标 < 100 ms；坏文件被跳过且接口 200；`tests/web/test_targets_robustness.py`。
- **风险**：mtime 排序依赖文件系统时间，Windows/POSIX 行为一致；索引方案需与 `save_target_state` 的写入点同步，避免双写。

### 2.5 安全评估（按本项目真实边界，不扩大防御面）

定位：本地单用户、操作者即机器所有者；`vulnclaw web` 默认绑定 `127.0.0.1`，非环回需 `--allow-remote` 且必须带 token cookie。基于这个边界，只列真正可达的问题：

1. **DNS rebinding（P2，推荐修）**：`auth.py:120-143` 明确把环回客户端视为可信。恶意网页可通过 DNS rebinding 让自己的域名解析到 `127.0.0.1`，从而无 token 调用 `/api/tasks/run`（等价命令执行）。修复成本极低：中间件校验 `Host` 头属于 `localhost`/`127.0.0.1`/`[::1]`/配置的 `VULNCLAW_WEB_PUBLIC_HOST`，不匹配返回 421；同时校验 `Origin`（若存在）同源。
2. **Token 生命周期（P3）**：token 永久有效、无轮换命令、Windows 无 ACL。补 `vulnclaw web --rotate-token` 与启动时打印「token 文件路径 + 权限」即可，不做账号体系。
3. **远程模式下的滥用面（P3）**：`--allow-remote` 时无速率限制。加一个进程内令牌桶（每分钟 N 次任务创建）即可，不引入中间件框架。
4. **已在做且做得对**：报告路径限制在 `SESSIONS_DIR`（`report_service.py:87-102`）、静态资源路径穿越防护（`app.py:85-97`）、CSP/X-Frame-Options/Referrer-Policy、`verify_execution_boundary.py` 的门禁断言、`exec_gate` 三档审批。

## 4. 功能蓝图

### 4.1 运行可靠性

#### F-01 任务事件总线（EventBus）

- **目标**：一个进程内、有序、可回放、有背压的事件通道，替代当前 history + queue 双通道。
- **方案**：`vulnclaw/web/event_bus.py`
  - `deque(maxlen=2000)` 环形缓冲 + `asyncio.Condition`；事件带 `seq`。
  - `subscribe(after_seq)` 异步生成器；消费者慢则跳过旧事件并标记 `gap`（不阻塞生产者）。
  - 事件落盘走 `RunContext.append_event` 同款 JSONL，进程重启后可从文件重建 `seq`。
- **落地**：`task_manager.publish` 改为委托 EventBus；`web/stream.py` 增加 `id:` 与心跳。
- **验收**：见 P1-02/04；`tests/web/test_event_bus.py`。
- **依赖**：无。

#### F-02 任务生命周期状态机

- **目标**：状态可枚举、转换有守卫、终态幂等。
- **方案**：`pending → queued → restoring → running → completed | failed | stopped | interrupted`；所有转换集中在 `task_manager._transition(task_id, to, **fields)`，非法转换抛 `ValueError`（内部错误，不外泄）。重启对账把非终态置 `interrupted`。
- **验收**：`tests/web/test_task_state_machine.py` 用参数化覆盖全部合法/非法转换。
- **依赖**：F-01（事件里的状态变更需要顺序）。

#### F-03 任务队列与优雅停机

- **目标**：并发可控、可取消、退出干净。
- **方案**：`asyncio.Semaphore` + FIFO deque；`lifespan` 关闭钩子；`SIGINT` 两阶段（停止接收 → cancel → 等 5 s → 强杀）。
- **验收**：见 P1-07；再加 `tests/web/test_shutdown_cleanup.py` 断言 MCP 子进程被回收。
- **依赖**：F-02。

### 4.2 可观测性

#### F-04 运行详情页

- **目标**：从「控制台日志流」升级为可回看的运行档案。
- **方案**：新增 `/api/runs`、`/api/runs/{run_name}`（读 `runs/<run>/run.json` + `events.jsonl`）；前端 `RunDetailPage`：时间线（阶段/工具/耗时）、证据抽屉、失败原因、续跑按钮。复用 `RunContext` 与 `summary`，不新增存储。
- **验收**：给定一份历史 run，页面能还原阶段耗时与终态；E2E 覆盖。
- **依赖**：F-01。

#### F-08 成本与 Token 仪表盘

- **目标**：让「这次扫了多少钱」可见。
- **方案**：`token_counter.py` 已有计数，聚合到 `TaskSummary`（新增 `tokens.input/output/total`、`cost_estimate`）；按模型价目表（配置项）估算；前端在任务卡与报告页展示。
- **验收**：mock LLM 返回固定 usage → 断言汇总与单价计算；报告页展示一致。
- **依赖**：无（纯聚合）。

#### F-09 审计与合规导出

- **目标**：把已有的 `constraint_audit`、`python_execute_audit`、审批记录变成可交付证据。
- **方案**：`/api/audit/export?format=jsonl|csv`；报告附「执行边界附录」（约束、违规事件、审批记录、工具清单）；复用 `web/services/constraint_audit_service.py`。
- **验收**：导出内容与接口数据一致；报告附录包含违规事件计数。
- **依赖**：F-07（报告中心）。

### 4.3 交付能力

#### F-05 项目 / 工作区模型

- **目标**：把扁平 `targets` 收进「项目」，支持授权范围模板与项目级报告。
- **方案**：`~/.vulnclaw/projects/<slug>/project.json`（名称、客户、授权窗口、默认 scope、目标列表）；target 记录增加 `project_id`（缺省 `default`）；Web 顶栏加项目切换；CLI 增加 `--project`。
- **验收**：创建项目 → 项目内启动任务 → 报告落 `projects/<slug>/reports/`；跨项目目标不串。
- **依赖**：P1-08（目标索引）。

#### F-06 发现工作台

- **目标**：发现项从「报告里的条目」变成可流转的工作项。
- **方案**：新增 `finding_status ∈ {new, triaged, confirmed, false_positive, fixed, risk_accepted}`、`note`、`assignee`（本地字符串）；写入 `target_state.finding_meta`（已有该结构，扩展字段即可）；前端表格支持状态筛选与批量操作；导出保留状态。
- **验收**：状态变更持久化并在报告标注；`tests/web/test_findings_lifecycle.py`。
- **依赖**：F-05。

#### F-07 报告中心 2.0

- **目标**：一次生成，多形态交付。
- **方案**：
  - 模板化（Jinja2 已在依赖中）：`templates/{pentest,executive,ctf}.md.j2`。
  - 脱敏：复用上下文压缩里已有的敏感字段脱敏规则（`authorization/cookie/api_key`）。
  - 相对路径（P2-06）+ 复现命令（`resume_command` 已有）。
  - 导出：`markdown | html | pdf`（已有 `pdf_exporter`）+ `json` + `sarif`（复用 `codescan/report.py:format_sarif` 的结构）。
- **验收**：同一 run 生成 5 种格式，`sarif` 通过 schema 校验；报告不含绝对路径与密钥。
- **依赖**：F-06。

#### F-10 集成导出（Jira / DefectDojo / Webhook）

- **目标**：让结果进入客户或团队既有系统。
- **方案**：`/api/integrations` 配置（URL + token 存配置，UI 只显示是否已配置）；`integrations/dispatch.py` 统一 `POST` 转换后的 findings；失败重试 3 次并记审计事件；默认关闭，需显式配置。
- **验收**：用本地 mock server 验证 payload 结构、重试、超时、幂等键；**禁止**在测试中打真实外部 API。
- **依赖**：F-07。

#### F-11 调度与通知

- **目标**：把 `persistent` 模式变成可排期的巡检。
- **方案**：进程内 `asyncio` 调度器（不引入 APScheduler）：`schedule: [{target, cron|interval, options}]` 存配置；触发即入 F-03 队列；完成/失败经 Webhook（飞书/Slack/通用 JSON）通知。
- **验收**：用可控时钟测试「到点入队、串行执行、失败告警」；Webhook 用 mock。
- **依赖**：F-03、F-10。

#### F-12 MCP 控制台

- **目标**：把 `doctor` 里的 MCP 状态搬进 UI，并支持启停与工具白名单。
- **方案**：`/api/mcp` 已返回诊断；新增 `POST /api/mcp/{name}/enable|disable`（写配置并热重启该 server）；工具白名单接入 `exec_gate` 的动作校验。
- **验收**：启停后 `diagnostics` 状态与工具数变化正确；禁用后对应工具调用被拒并记审计。
- **依赖**：F-03（生命周期统一管理）。

#### F-13 离线 / 内网模式

- **目标**：无外网环境可用（内网渗透、靶场、断网客户现场）。
- **方案**：`--offline` 关闭知识库在线更新与 provider 探测；KB 支持预打包索引；Ollama 预设已存在，补「离线体检」到 `doctor`。
- **验收**：断网环境 `vulnclaw doctor` 不报错、不挂起；`solve` 可跑通本地模型。
- **依赖**：无。

#### F-14 插件生态

- **目标**：第三方检测插件无需改仓库即可加载。
- **方案**：`importlib.metadata.entry_points(group="vulnclaw.plugins")` 发现；`PluginManifest` 声明 `permissions`（network/filesystem/subprocess）与 `risk`；加载前校验 `plugin_id` 唯一与版本兼容。
- **验收**：在 `tests/plugins` 放一个通过 entry-point 安装的样例包，验证发现、权限拒绝、版本不兼容提示。
- **依赖**：F-12。

## 5. 关键技术决策（方案对比）

### 5.1 事件总线与持久化

| 方案 | 做法 | 可行性 | 成本 | 维护 | 性能 | 扩展性 | 风险 | 结论 |
|------|------|--------|------|------|------|--------|------|------|
| A. 队列 + 历史（现状） | 两条通道各自投递 | 5 | 1 | 2 | 2 | 2 | 高（重复/无界） | 淘汰 |
| B. 环形缓冲 + `asyncio.Condition` + JSONL 落盘 | 单通道、单调 seq、慢消费者跳过 | 5 | 3 | 4 | 5 | 4 | 低 | **推荐** |
| C. 引入 SQLite 事件表 | 用 SQL 查询/分页 | 4 | 4 | 4 | 4 | 5 | 中（并发写锁、迁移） | 第二阶段可选 |

推荐 B 的理由：不新增依赖、与 `RunContext.append_event` 的 JSONL 语义一致、重启可重建 seq；C 的查询能力在「运行详情页」需要跨 run 检索时再评估，不要提前引入。

### 5.2 任务调度

| 方案 | 做法 | 可行性 | 成本 | 维护 | 性能 | 扩展性 | 风险 | 结论 |
|------|------|--------|------|------|------|--------|------|------|
| A. 直接 `create_task`（现状） | 无上限 | 5 | 1 | 2 | 2 | 1 | 高 | 淘汰 |
| B. 进程内信号量 + FIFO | 单进程、`queued` 状态 | 5 | 2 | 4 | 4 | 3 | 低 | **推荐** |
| C. Celery/Redis 队列 | 独立 worker | 2 | 5 | 2 | 4 | 5 | 高（部署复杂度、Windows 支持差） | 不做 |

### 5.3 目标索引

| 方案 | 做法 | 可行性 | 成本 | 维护 | 性能 | 扩展性 | 风险 | 结论 |
|------|------|--------|------|------|------|--------|------|------|
| A. 全量解析（现状） | `glob` + `json.loads` 全部 | 5 | 1 | 4 | 1 | 2 | 高（2.7 s / 单坏文件 500） | 淘汰 |
| B. mtime 排序 + 截断 + 单文件容错 | 不改存储结构 | 5 | 1 | 5 | 4 | 3 | 低 | **立即做** |
| C. `index.json` 增量索引 | 写入点维护摘要 | 4 | 3 | 3 | 5 | 5 | 中（双写一致） | 第二阶段 |

### 5.4 前端测试栈

| 方案 | 做法 | 成本 | 覆盖能力 | 维护 | 结论 |
|------|------|------|----------|------|------|
| A. 只补 Vitest + RTL | 单测/组件测 | 2 | 中 | 5 | 与 B 并行，先落 |
| B. Vitest + Playwright | 加 3 条 E2E | 3 | 高 | 4 | **推荐组合** |
| C. 只上 E2E | 纯浏览器 | 4 | 中（慢、脆） | 2 | 不做 |

### 5.5 版本单一来源

| 方案 | 做法 | 成本 | 风险 | 结论 |
|------|------|------|------|------|
| A. 保留多处手写 + 测试断言相等 | 每处都改 | 1 | 中（漏改） | 可作为过渡 |
| B. `vulnclaw.__version__` 为唯一真值，其余引用/注入 | web 引用、前端 Vite `define` | 2 | 低 | **推荐** |
| C. 构建时生成 `_version.py` | hatch hook | 3 | 中（本地未构建时缺失） | 不需要 |

约束：测试只断言行为与无障碍语义，不测实现细节；网络层用 `msw` 或 `vi.stubGlobal("fetch")`，不打真实后端。

### 7.3 长稳剧本（`scripts/soak_web.py`）

1. 启动 `vulnclaw web`（`VULNCLAW_CONFIG_DIR` 指向临时目录）。
2. 每 5 s 提交一个 `codescan` 任务（无需 LLM，纯本地，避免付费与网络）。
3. 并发 3 个 SSE 客户端，每 60 s 主动断开重连。
4. 每 10 min 记录：RSS、线程数、句柄数、`web_tasks.json` 大小、事件文件总大小、`running/queued` 计数。
5. 24 h 后断言：RSS 增长 < 10%、无 `running` 残留、无孤儿子进程、磁盘增长线性且受保留策略约束。

> 说明：用 `codescan` 而非 `recon`，避免真实 LLM 调用与对外扫描；如必须验证 LLM 路径，使用本地 mock server。

## 9. 风险与回滚

| 风险 | 触发场景 | 缓解 | 回滚 |
|------|----------|------|------|
| 事件模型改动导致前端停更 | `event:` 名或 seq 变更 | 先兼容旧字段（保留 `task_id/timestamp`），前端与后端同 PR | 恢复旧 `stream_events` |
| 状态枚举新增 `interrupted` 影响旧客户端 | 第三方脚本判断状态 | 视为非终态失败类；CHANGELOG 明示；API 文档更新 | 前端映射表回退 |
| `stop` 语义由 200 改 409 | 现有自动化 | 返回体保留 `task_id/status`，文档标注变更 | 恢复 200 + 状态守卫 |
| 持久化格式迁移失败 | 旧 `web_tasks.json` | 首次启动自动迁移并备份为 `.bak`，失败则从空状态启动并告警 | 恢复 `.bak` |
| 调度器引入后台任务泄漏 | 长跑 | 单一调度循环 + `finally` 取消；soak 覆盖 | 关闭调度配置项 |
| 前端测试引入构建复杂度 | CI 时长 | Vitest 只跑单测，E2E 单独 job，按需触发 | 移除 job |

## 10. 明确不做（防过度工程）

1. 不引入 Redis / Celery / Postgres / 消息队列：单机单用户，进程内足够。
2. 不重写 `WebTaskManager` 为分布式任务系统。
3. 不重构 `vulnclaw/cli/main.py`：只做「命令体内延迟导入」与「补预检」两处局部修改。
4. 不改 Rust TUI 架构，不复活 Textual 实现。
5. 不为本地场景加账号体系、RBAC、OAuth；VPS 多用户单独立项。
6. 不加 feature flag、配置开关矩阵、兼容层；需要行为差异时用**参数**（如 `raise_on_error`）而非开关。
7. 不加遥测、不上报任何使用数据。
8. 不做与定位无关的功能（自动修复代码、聊天机器人、模型微调）。
9. 不为「理论上可能」的场景写防御代码；安全问题只覆盖本项目真实可达路径（见 2.5）。

## 附录 C：术语

| 术语 | 含义 |
|------|------|
| 运行（run） | 一次任务执行，对应 `~/.vulnclaw/runs/<run_name>/` |
| 目标状态（target state） | 某目标跨运行的累积状态与快照，对应 `~/.vulnclaw/targets/<target>/` |
| 证据（evidence） | 工具调用的原始输出与派生摘要，存于 `AgentState.evidence` |
| 事件（event） | 任务生命周期中的结构化通知，SSE 推送给前端 |
| 终态 | `completed` / `failed` / `stopped` / `interrupted` |
| 对账（reconcile） | 进程启动时把持久化的非终态任务修正为 `interrupted` |
| 写放大 | 单次事件触发整文件重写，成本随累计数据线性增长 |
| 慢消费者 | 订阅速度低于生产速度的 SSE 客户端 |
